# QA 검증 수준과 증거를 쉽게 읽는 법

## Why

kyle이 테스트 이름만 보고도 무엇을 진짜 확인했는지, 무엇이 가짜 환경에서만 통과했는지 구분해 PASS 보고를 과신하지 않게 한다.

이 문서는 [docs/TODO.md](../TODO.md)의 11번 항목을 따라, 검증 이름과 기록을 읽는 방법을 설명한다. 어려운 말 대신 "어디까지 실제로 확인했나"를 기준으로 판단한다.

## 먼저 기억할 한 문장

테스트가 초록색으로 끝났다는 사실은 **그 테스트가 건드린 범위만** 확인한다. 앱을 켜지 않은 시험은 앱이 잘 켜진다는 뜻이 아니고, 가짜 입력을 쓴 시험은 실제 사용자 환경에서도 된다는 뜻이 아니다.

## 검증 이름은 확인한 세계를 알려 준다

아래 검증은 서로 대신할 수 없다. 각각 다른 문을 열어 보는 검사다.

| 이름에 보이는 말               | 쉽게 말하면                                | 확인하는 것                                                      | 확인하지 못하는 것                                 |
| ------------------------------ | ------------------------------------------ | ---------------------------------------------------------------- | -------------------------------------------------- |
| `source-review`                | 코드를 읽는 검사                           | 조건, 분기, 연결이 의도대로 쓰였는지                             | 코드가 실제로 실행되는지                           |
| `focused` / `unit` / `fixture` | 부품 하나를 가짜 재료로 검사               | 좁은 규칙과 예외 처리                                            | 실제 앱, 실제 파일, 실제 CLI 연결                  |
| `full-test`                    | 정해 둔 전체 시험 묶음을 실행              | 여러 부품의 시험 결과                                            | 시험이 모두 가짜 환경이면 실제 앱의 연결 상태      |
| `local-build`                  | 소스를 실행 파일로 만드는 검사             | 빌드(컴파일)가 끝나 실행 파일이 생겼는지                         | 그 파일이 실제로 켜지는지, CLI와 대화하는지        |
| `package`                      | 실행 파일을 설치 묶음으로 싸는 검사        | 설치 묶음(패키지) 파일이 만들어지는지                            | 묶음이 만들어졌다고 앱이 켜진 것은 아님            |
| `package-app-startup`          | 포장된 앱(패키지 앱)을 실제로 켜 보는 검사 | 패키지 앱이 시작되고 창이 뜨는지                                 | 앱이 CLI 요청에 응답하고 상태가 바뀌는지           |
| `daemon-startup`               | 창 없는 백그라운드 엔진만 켜 보는 검사     | 데몬(백그라운드 엔진)의 시작과 준비 신호                         | 데스크톱 화면과 앱-CLI 전체 왕복                   |
| `cli-only`                     | CLI(명령줄 도구)만 단독으로 부르는 검사    | CLI가 명령을 받고 보냈는지                                       | 앱이 실제로 받고 응답했는지, 상태가 바뀌었는지     |
| `dev-isolated-e2e`             | 개발 앱을 격리 데이터로 켜고 왕복하는 검사 | 개발 앱 기동, 실제 CLI 요청, 앱의 실제 응답과 상태               | 포장된 앱(패키지 앱)에서도 같은지                  |
| `packaged-app-e2e`             | 포장된 앱을 켜고 CLI 왕복하는 검사         | 패키지 앱 기동, CLI 요청, 앱 응답과 상태 변화                    | 사람이 화면을 클릭하는 Computer Use                |
| `official-run`                 | 실제 실행 기록(Run)으로 확인하는 검사      | taskId와 dispatchId가 있는 Run 수명주기, worker_done과 상태 변화 | 가짜 데이터(fixture)나 CLI 단독 성공으로 대체 불가 |
| `computer-use`                 | 화면을 사람처럼 클릭하는 검사              | 접근성 권한과 화면 조작으로 데스크톱 UI 동작                     | CLI 왕복이 정상이라는 것                           |
| `independent-review`           | 다른 사람이 다시 보는 검사                 | 앞선 결과가 현재 코드와 증거에 맞는지                            | 빠진 실행을 대신해 주는 것                         |

### source review: 코드를 읽는 검사

`source-review`는 소스 코드와 변경 내용을 눈으로 읽는다. 예를 들어 "실패하면 멈추는가", "다른 판의 실행 기록을 건드리지 않는가" 같은 약속을 코드에서 확인한다.

이 검사는 중요한 첫 단계지만, 코드를 읽었다고 실행 결과가 생기지는 않는다. `source-review PASS`를 `앱 실행 PASS`로 읽으면 안 된다.

### focused/unit fixture: 부품 하나와 가짜 재료

`focused` 또는 `unit` 검사는 작은 부품을 빠르게 검사한다. 가짜 시험 재료(`fixture`)는 시험에 넣는 가짜 입력·가짜 파일·가짜 응답이다. 예를 들어 "잘못된 입력이면 오류를 돌려주는가"를 실제 서버 대신 미리 만든 값으로 확인할 수 있다.

이 검사는 작은 규칙이 깨졌는지 찾는 데 좋다. 하지만 앱을 켜지 않았다면 앱 기동을, 실제 파일을 쓰지 않았다면 파일 권한을, 실제 CLI를 연결하지 않았다면 연결을 증명하지 않는다.

### full test: 시험 묶음 전체

`full-test`는 프로젝트가 정한 전체 또는 큰 범위의 시험 묶음이다. 좁은 시험 하나보다 넓게 볼 수 있지만, 그 안의 시험들이 전부 fixture와 가짜 서버만 사용한다면 여전히 가짜 환경의 성공이다.

따라서 `full-test PASS` 다음에 바로 "실제 앱도 정상"이라고 쓰지 않는다. 실제 앱을 확인하려면 아래의 `dev-isolated-e2e` 또는 `packaged-app-e2e` 결과가 따로 있어야 한다.

### local build: 실행 파일을 만드는 단계

`local-build`는 소스를 실행 가능한 결과물로 만드는 단계다. 빌드가 성공했다는 것은 실행 파일이 생겼다는 뜻이지, 그 파일이 켜진다는 뜻은 아니다.

빌드가 성공해도 다음은 아직 모른다.

- 포장(패키지)이 되었는가
- 앱이 시작하는가
- 실행 중인 앱이 CLI의 요청을 받는가
- CLI 요청과 앱 응답이 끝까지 왕복하는가

이것들은 아래 단계에서 각각 확인한다.

### package: 설치 묶음을 만드는 단계

`package`는 빌드 결과물을 설치 묶음(패키지 번들)으로 싸는 단계다. 패키지 파일이 만들어졌다는 것은 묶음이 생겼다는 뜻이지, 그 묶음 속의 앱이 켜진다는 뜻은 아니다.

패키지 생성 성공과 패키지 앱 기동 성공은 서로 다른 단계다. 묶음을 만드는 데 성공했다고 "패키지 앱이 정상적으로 켜진다"고 쓰지 않는다. 앱이 실제로 켜지는지는 다음 단계인 `package-app-startup`에서 확인한다.

### package app startup: 포장된 앱을 켜 보는 단계

`package-app-startup`은 포장된 앱(패키지 앱)을 실제로 실행해 시작하고 창이 뜨는지 확인한다. 이것은 패키지 생성(`package`)과 다른 별도 단계다.

패키지 앱이 켜졌어도 다음은 아직 모른다.

- 켜진 앱이 CLI 요청을 받고 응답하는가
- 요청과 응답이 끝까지 왕복하는가
- 필요한 상태가 실제로 바뀌었는가

이것들은 `packaged-app-e2e`에서 확인한다.

### daemon startup: 창 없는 엔진 점화

`daemon-startup`은 화면을 띄우지 않고 백그라운드 엔진을 잠깐 켜서 "프로세스가 시작했고 준비됐는가"를 확인한다. 데몬이 준비됐다는 것은 데몬의 시작 문이 열렸다는 뜻이지, 데스크톱 앱 전체가 정상이라는 뜻은 아니다.

데몬 점화가 PASS여도 앱 창, 앱의 사용자 데이터, 앱-CLI 왕복은 별도 검사가 남는다.

### CLI 단독 호출: 보냈다고 받은 것은 아니다

`cli-only`는 CLI(명령줄 도구)만 단독으로 실행해 명령을 보내는 검사다. CLI가 명령을 수락하고 보냈다는 것은 보낸 쪽의 문이 열렸다는 뜻이다.

하지만 CLI 단독 호출은 **받는 쪽까지 확인하지 않는다**. 다음은 아직 모른다.

- 앱이 실제로 그 요청을 받았는가
- 앱이 응답을 돌려주었는가
- 앱의 상태가 실제로 바뀌었는가

"CLI가 전송에 성공했다"는 것과 "앱이 응답했다"는 다른 말이다. 우체부가 편지를 배달한 것과 받는 사람이 읽고 답장한 것은 다른 일이다. CLI 송신 성공을 `dev-isolated-e2e` 또는 `packaged-app-e2e`의 왕복 성공으로 읽으면 안 된다.

### 개발 앱 격리 E2E: 진짜 앱과 CLI의 왕복 (개발 모드)

이 문서에서 "개발 앱 실기동 E2E"라고 부르는 검사는 다음 뜻이다.

1. 개발 모드 앱(소스에서 바로 켜는 앱)을 시험용으로 하나 더 켠다.
2. 앱에게는 실제 사용자 집처럼 보이지만 실제 집과는 분리된 **격리된 가짜 집**을 준비한다. 이곳은 별도 임시 사용자 데이터와 작업 폴더라서 공식 앱의 데이터와 섞이지 않는다.
3. CLI가 실행 중인 앱에 요청을 보낸다.
4. 앱이 실제로 응답하고, 필요한 상태가 실제 결과로 바뀌는지 확인한다.
5. 시험이 끝나면 공식 앱과 공식 데이터, 다른 실행 기록에 변화가 없었는지 확인한다.

이것이 "왕복"인 이유는 한쪽 말만 듣지 않기 때문이다. CLI가 편지를 보낸 것만 보지 않고, 진짜 앱이 그 편지를 받고 답장을 돌려준 것까지 본다. 가짜 함수가 `성공`이라고 말한 것과는 다르다.

개발 앱 격리 E2E는 개발 모드에서 실행한 것이므로, 포장된 앱(패키지 앱)에서도 같은 결과가 나오는지는 `packaged-app-e2e`에서 따로 확인한다.

Electron E2E를 실행할 때는 [tests/e2e/AGENTS.md](../../tests/e2e/AGENTS.md)의 `--mode e2e` 빌드 규칙도 함께 따른다. 빌드가 오래됐거나 다른 모드로 만들어졌다면 시험이 멈출 수 있으므로, 그런 실패를 앱 기능 실패로 단정하지 말고 환경을 먼저 확인한다.

### 패키지 앱 E2E: 포장된 앱으로 왕복하는 검사

`packaged-app-e2e`는 포장된 앱(패키지 앱)을 실제로 켜고 CLI 왕복을 확인하는 단계다. 개발 앱 격리 E2E(`dev-isolated-e2e`)가 개발 모드 앱을 쓴다면, 이 검사는 사용자가 받는 그 포장물(패키지)을 켠다는 점이 다르다.

패키지 앱은 서명, 권한, 경로가 개발 앱과 다를 수 있으므로, 개발 앱 E2E가 PASS여도 패키지 앱 E2E가 실패할 수 있다. 두 검사는 서로 대신할 수 없는 별도 단계다.

### 공식 Run: 실제 실행 기록으로 확인하는 단계

`official-run`은 실제 Orca 실행 기록(Run) 안에서 일어난 일을 증거로 삼는다. 여기에는 `taskId`와 `dispatchId`가 있고, 작업자(worker)가 보낸 `worker_done` 신호와 상태 변화가 기록된다.

이 단계의 핵심은 **가짜 데이터(fixture)나 CLI 단독 성공으로 대체할 수 없다**는 것이다.

- `worker_done`은 실제 Run 수명주기 안에서 현재 task와 dispatch에 대응할 때만 의미가 있다. 같은 Run에서 우연히 통과한 것이 worker_done을 대신하지 않는다.
- CLI 단독으로 요청을 보낸 것만으로 앱의 상태 변화나 worker 완료를 증명하지 못한다.
- fixture 시험이 PASS여도 실제 Run에서 일어난 일과는 다르다.

공식 Run 증거는 실행 기록의 식별자(taskId, dispatchId)와 상태 변화 출력 원문, 그리고 작업자가 보낸 `worker_done` 신호의 원문까지 함께 남겨야 다시 확인할 수 있다.

## Computer Use는 이번 문서의 후순위 검사다

Computer Use는 사람이 화면을 클릭하듯 접근성 권한과 화면 조작으로 데스크톱 UI를 시험하는 방식이다. 이번 QA 방식 문서에서는 Computer Use를 기본 완료 조건에서 제외하고 후순위로 둔다.

이유는 간단하다. 화면 권한, 운영체제 창 상태, 포커스 같은 별도 조건이 많아서 CLI 왕복과 다른 종류의 문제가 섞이기 때문이다. Computer Use가 아직 실행되지 않았다는 이유만으로 CLI 실기동 E2E를 가짜라고 부르지는 않지만, 반대로 Computer Use가 PASS여도 CLI 왕복 PASS를 대신하지 못한다.

Computer Use와 `independent-review`는 서로 다른 별개 근거다. 화면 조작으로 UI를 확인하는 것과 다른 사람이 코드와 증거를 대조하는 것은 다른 검사이며, 한쪽이 다른 쪽을 대신하지 않는다.

## independent review: 두 번째 눈으로 다시 확인하기

`independent-review`는 앞선 작업자의 보고서를 믿고 도장을 찍는 일이 아니다. 다른 검수자가 **현재 작업 공간(worktree)의 소스·변경 내용·실행 명령·출력 원문**을 직접 다시 보고, 보고서와 실제 상태가 맞는지 대조한다.

독립 검수자는 다음을 확인한다.

- 보고서에 적힌 명령을 실제 범위와 비교한다.
- 실행 대상이 현재 작업 공간(worktree)과 같은지 확인한다.
- `fixture` 성공을 `live` 성공으로 부풀리지 않았는지 확인한다.
- CLI 단독 성공을 앱 왕복 성공으로 부풀리지 않았는지 확인한다.
- 패키지 생성 성공을 패키지 앱 기동 성공으로 섞지 않았는지 확인한다.
- 빠진 단계, 서로 맞지 않는 출력, 오래된 결과를 표시한다.
- 필요한 경우 같은 좁은 검사를 다시 실행한다.

독립 검수 PASS는 "한 번 더 봤다"는 뜻이다. 실기동 E2E가 빠져 있으면 독립 검수만으로 그 빈칸이 채워지지 않는다.

## 증거는 요약이 아니라 명령과 출력 원문으로 남긴다

"테스트 통과"라는 한 줄은 나중에 다시 확인하기 어렵다. 각 검증에는 다음 정보를 한 묶음으로 남긴다.

| 기록할 것     | 적는 내용                                                                                                                |
| ------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 검증 이름     | `focused-unit-fixture`, `cli-only`, `dev-isolated-e2e`, `packaged-app-e2e`, `official-run`처럼 실제 단계를 드러내는 이름 |
| 목표          | 무엇을 확인하려 했는지 한 문장                                                                                           |
| 환경          | OS, 작업 공간(worktree), 앱 종류(개발 앱 또는 패키지 앱), 앱 경로, 격리 데이터 경로, 사용한 실행 파일                    |
| **명령 원문** | 복사해서 다시 실행할 수 있는 명령 전체                                                                                   |
| **출력 원문** | 명령이 실제로 낸 출력 전체. 성공 한 줄로 줄이지 않는다.                                                                  |
| 판정          | `PASS`, `PARTIAL`, `FAIL` 중 하나와 이유                                                                                 |
| 남은 관문     | 아직 확인하지 않은 다음 단계                                                                                             |

검증 이름을 적을 때 단계를 섞지 않는다. `cli-only`로 보낸 것을 `dev-isolated-e2e`라고 부르지 않고, `package`로 만든 것을 `package-app-startup`이라고 부르지 않는다.

기록 파일에는 아래처럼 고정된 모양을 쓴다.

```text
검증 이름: dev-isolated-e2e-cli
목표: 격리된 가짜 집의 앱과 CLI가 한 번 왕복하는지 확인
환경: <OS / 작업 공간(worktree) / 개발 앱 경로 / 격리 데이터 경로>

명령 원문:
$ <실제로 실행한 명령 전체>

출력 원문:
<명령이 실제로 출력한 내용 전체>

판정: PASS
이유: <출력에서 확인한 사실>
남은 관문: <없음 또는 아직 필요한 검증>
```

출력 원문에는 비밀 키나 개인 정보가 들어갈 수 있다. 그런 경우 원문 증거는 접근이 제한된 증거 파일(evidence file)에 보관하고, 보고서나 대화에는 값을 복사하지 않는다. 원문을 가렸다면 `출력 원문 일부 가림`이라고 표시해, 완전한 원문이 아님을 숨기지 않는다.

## PASS, PARTIAL, FAIL을 나누는 법

### PASS

그 검증이 약속한 범위를 실제 증거가 모두 덮으면 `PASS`다.

- `source-review PASS`: 코드를 읽고 약속된 분기와 범위를 확인했다.
- `focused-unit-fixture PASS`: 좁은 규칙이 준비한 fixture에서 맞게 동작했다.
- `full-test PASS`: 정한 전체 시험 묶음이 끝까지 통과했다.
- `local-build PASS`: 소스를 실행 파일로 빌드했다.
- `package PASS`: 실행 파일을 설치 묶음(패키지)으로 포장했다.
- `package-app-startup PASS`: 포장된 앱이 실제로 시작하고 창이 떴다.
- `daemon-startup PASS`: 격리된 데몬이 시작하고 준비 신호를 냈다.
- `cli-only PASS`: CLI가 명령을 수락하고 보냈다.
- `dev-isolated-e2e PASS`: 격리된 가짜 집에서 개발 앱이 켜지고 CLI 왕복이 성공했으며 공식 데이터, 프로세스가 변하지 않았다.
- `packaged-app-e2e PASS`: 포장된 앱이 켜지고 CLI 왕복이 성공했다.
- `official-run PASS`: taskId와 dispatchId가 있는 실제 Run에서 worker_done과 상태 변화가 확인되었다.
- `computer-use PASS`: 접근성 권한과 화면 조작으로 UI 동작을 확인했다.
- `independent-review PASS`: 다른 검수자가 현재 상태와 증거를 직접 대조해 막을 문제를 찾지 못했다.

### PARTIAL

일부 문은 열렸지만 필요한 문이 아직 남았거나, 확인 범위가 가짜 환경에 머물면 `PARTIAL`이다.

예를 들면 다음과 같다.

- unit과 full test는 PASS지만 실기동 E2E를 아직 하지 않았다.
- 빌드는 됐지만 패키지 생성과 패키지 앱 기동을 하지 않았다.
- 패키지는 만들어졌지만 패키지 앱을 켜 보지 않았다.
- CLI 단독 호출은 성공했지만 앱 왕복(E2E)은 하지 않았다.
- 개발 앱 E2E는 PASS지만 패키지 앱 E2E는 하지 않았다.
- 데몬은 켜졌지만 데스크톱 앱은 켜지지 않았다.
- 독립 검수가 아직 시작되지 않았다.
- 명령은 남았지만 출력 원문이 없어 결과를 다시 확인할 수 없다.

`PARTIAL`은 실패라는 뜻이 아니라 "아직 완료 도장을 찍지 말자"는 뜻이다.

### FAIL

실제로 실패했거나, 안전하지 않은 범위가 확인되면 `FAIL`이다.

- 필요한 시험 명령이 오류로 끝났다.
- 진짜 앱이 격리된 가짜 집에서 시작하지 않았다.
- 앱은 켜졌지만 CLI 요청과 응답의 왕복이 끊겼다.
- 공식 데이터나 다른 실행 기록을 건드렸다.
- 보고서의 명령·출력과 현재 코드가 서로 맞지 않는다.
- CLI 단독 성공을 앱 왕복 성공으로 적었다가 들통났다.
- 패키지 생성 성공을 패키지 앱 기동 성공으로 섞어 적었다.

실패한 관문 뒤에 있는 검증을 억지로 PASS로 올리지 않는다. 원인을 적고 필요한 조건을 고친 뒤 같은 검증을 다시 실행한다.

## 최종 보고서에서 과신하지 않는 순서

실제 앱과 CLI까지 확인했다는 말을 하려면 다음 줄을 따로 보여 준다.

1. source review 결과
2. focused/unit fixture 결과
3. full test 결과
4. local build 결과
5. package 결과 (패키지 파일 생성)
6. package-app-startup 결과 (패키지 앱 기동)
7. daemon startup 결과 (필요한 경우)
8. cli-only 결과 (CLI 단독 호출)
9. dev-isolated-e2e 결과 (개발 앱 격리 E2E)
10. packaged-app-e2e 결과 (패키지 앱 E2E)
11. official-run 결과 (실제 Run)
12. computer-use 결과 (후순위)
13. independent-review 결과
14. 각 단계의 명령 원문과 출력 원문 위치

특히 2번, 3번, 8번만 PASS라면 "부품 시험, CLI 단독 송신 PASS"라고 쓴다. 9번이나 10번까지 PASS하고 격리, 무변경 대조도 끝났을 때에만 "실제 앱과 CLI 왕복 PASS"라고 쓴다. 11번까지 PASS해야 "실제 Run에서 확인했다"고 쓴다. 운영 앱 교체나 배포 같은 다음 행동은 필요한 모든 관문과 독립 검수가 PASS인 뒤에만 판단한다. 운영 앱과 데이터 보존 절차는 [Orca Kyle 설치, 실행, 복구](../readme/orca-kyle-operations.md)도 함께 확인한다.
